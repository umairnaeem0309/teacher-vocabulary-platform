# ENGLISH–POLISH VOCABULARY PLATFORM

## SIMPLIFIED PRODUCT REQUIREMENTS / BRD

---

# 1. PRODUCT PURPOSE

Build a complete, production-ready web application for teaching English to Polish-speaking students.

The primary purpose of the platform is to provide the teacher with a large, high-quality English–Polish vocabulary database and a simple tool for:

* finding vocabulary
* filtering vocabulary
* selecting vocabulary
* organizing vocabulary into reusable sets
* assigning vocabulary to individual students
* tracking each student's vocabulary learning state
* conducting manual vocabulary reviews
* recording review results
* using FSRS to determine the next review date

The application should be a practical teacher vocabulary management and review system rather than a general-purpose learning platform.

The teacher-facing interface should be fast, information-dense and easy to use during real teaching.

The system must make it possible to find relevant vocabulary from natural concepts or topics without requiring the teacher to know the individual English words beforehand.

---

# 2. USERS

## 2.1 TEACHER

The teacher has a secure account and can:

* create and manage students
* search vocabulary
* perform semantic vocabulary searches
* filter vocabulary
* browse vocabulary in a spreadsheet-like interface
* create reusable vocabulary sets
* assign vocabulary to students
* see vocabulary already assigned to a student
* filter vocabulary that is not yet assigned to a student
* see student learning states
* see due and overdue vocabulary
* conduct manual vocabulary reviews
* record review results
* view next review dates
* manually change student vocabulary states
* manage student access
* import and export vocabulary data
* copy vocabulary for sending to students

---

# 3. CORE PRODUCT CONCEPT

The system has two primary data areas:

## VOCABULARY

The global master English–Polish vocabulary database.

## STUDENT LEARNING

The individual relationship between a student and each master vocabulary sense.

The master vocabulary must remain independent from student learning data.

A single master vocabulary sense can therefore be assigned to many students without creating duplicate master records.

The core workflow is:

FIND → FILTER → SELECT → ASSIGN → REVIEW → RECORD RESULT → FSRS SCHEDULES NEXT REVIEW

Search must support both:

* direct lexical search
* conceptual/semantic search

The teacher should be able to search for a concept such as:

* vacation
* cooking
* things I need at an airport
* problems at a hotel
* vocabulary for describing personality
* buying a house

without knowing the individual English vocabulary items beforehand.

---

# 4. MASTER VOCABULARY DATABASE

The platform must contain a large English–Polish vocabulary database capable of supporting hundreds of thousands of vocabulary senses if necessary.

The database should be comprehensive.

The system must NOT remove vocabulary merely because it is:

* obscure
* rare
* archaic
* obsolete
* technical
* specialized
* uncommon
* difficult

Such vocabulary may receive a lower Vocabulary Priority score, but it must remain in the master database when supported by the source data.

The purpose of the priority system is to help the teacher find the most useful vocabulary quickly, not to delete less useful vocabulary.

The search system must be capable of surfacing relevant vocabulary even when the vocabulary item does not literally contain the teacher's search term.

---

# 5. SENSE-BASED VOCABULARY

Vocabulary must be stored by individual sense rather than treating every English word as one learning item.

Example:

BANK

### Sense 1

* financial institution
* Polish: bank
* A2
* MONEY & BANKING

### Sense 2

* side of a river
* Polish: brzeg
* B2
* GEOGRAPHY

These are separate vocabulary senses.

Each sense may have its own:

* English form
* definition
* Polish translation(s)
* part of speech
* CEFR level
* example sentence
* frequency information
* Vocabulary Priority
* categories or semantic associations
* semantic embedding
* provenance
* quality information

The same English word can therefore have different priority, CEFR, frequency and translations for different senses.

---

# 6. CEFR

The vocabulary database must support:

* A1
* A2
* B1
* B2
* C1
* C2

CEFR should be associated with the vocabulary sense whenever reliable source data supports sense-level classification.

If multiple sources provide different CEFR information, the system should preserve the source information and calculate an appropriate normalized level where possible.

CEFR represents difficulty.

CEFR must NOT be treated as a direct measure of usefulness.

A C2 word can have VERY HIGH Vocabulary Priority if it is common and useful.

An A2 word can have LOW Vocabulary Priority if it is rare or highly specialized.

Teachers must be able to filter by CEFR independently of Vocabulary Priority.

---

# 7. VOCABULARY PRIORITY

Each vocabulary sense should have a calculated Vocabulary Priority.

Vocabulary Priority estimates how useful the sense is for English learners.

The score must be separate from:

* CEFR level
* raw frequency rank
* student learning state

Potential signals include:

* sense frequency
* overall word frequency
* frequency across available corpora/datasets
* NGSL or other frequency evidence
* CEFR evidence
* breadth of real-world use
* number of relevant contexts/domains
* learner relevance
* source agreement
* whether the sense is modern
* archaic/obsolete indicators
* rare indicators
* technical/specialized indicators
* proper-name indicators
* quality and confidence of lexical data

The exact mathematical formula may be designed by the developer.

The result must reflect teaching usefulness rather than simply CEFR difficulty.

The priority calculation should preferably be deterministic and reproducible.

An external LLM must not be required to calculate Vocabulary Priority for every vocabulary sense.

---

# 8. PRIORITY PRINCIPLES

The following principles are mandatory:

1. All supported vocabulary senses should remain in the master database.

2. C2 vocabulary must NOT automatically receive low priority.

3. CEFR must NOT be used as a proxy for usefulness.

4. Frequency should be an important signal, but frequency alone should not determine usefulness.

5. A sense should be evaluated independently from other senses of the same word.

6. Rare, archaic and specialized vocabulary should generally receive lower priority when appropriate, but must not be deleted.

7. Broadly useful vocabulary should receive higher priority even when it is C1 or C2.

8. The system should allow the teacher to access all vocabulary regardless of priority.

9. Vocabulary relevance should not depend exclusively on manually assigned categories.

---

# 9. PRIORITY LEVELS

The calculated numerical Vocabulary Priority Score should be converted into simple teacher-facing categories.

Recommended levels:

* VERY HIGH
* HIGH
* MEDIUM
* LOW
* VERY LOW

The teacher should normally see the priority category rather than the mathematical score.

The numerical score should remain available internally for sorting and future improvements.

---

# 10. FREQUENCY VS PRIORITY

The system must store objective frequency information separately from Vocabulary Priority.

Frequency answers:

"How often does this word/sense occur?"

Vocabulary Priority answers:

"How useful is this vocabulary sense for an English learner?"

These are related but different measurements.

For example, a very frequent word can still have a particular sense that is less useful to general learners.

Likewise, a C2 word can be less frequent than an A2 word but still be highly useful for educated, professional, academic or news-related English.

---

# 11. TEACHER PRIORITY OVERRIDE

The system should allow the teacher to override the general Vocabulary Priority for teaching purposes when appropriate.

The global calculated priority remains unchanged.

A teacher-specific priority may be stored separately.

For example:

Global Priority: MEDIUM

Teacher Priority for John: HIGH

This allows the teacher to identify vocabulary that is especially relevant to an individual student's:

* profession
* interests
* goals
* current lesson
* upcoming situation
* personal vocabulary needs

---

# 12. VOCABULARY RELEVANCE AND SEMANTIC RETRIEVAL

The system must support finding vocabulary based on meaning and conceptual relevance rather than requiring an exact word match.

A teacher should be able to enter searches such as:

* vacation
* cooking
* airport problems
* hotel vocabulary
* things you need when traveling
* describing someone's personality
* buying a house
* talking about work
* money problems
* going to the doctor

The system should return vocabulary senses that are relevant to the concept even when the exact search word does not appear in:

* the English word
* the Polish translation
* the definition

Semantic retrieval should therefore be supported.

The system should NOT require an external LLM request every time a teacher performs a search.

The preferred architecture is a hybrid search system using a combination of:

* PostgreSQL text search
* exact lexical matching
* definitions
* translations
* existing lexical metadata
* categories where available
* WordNet/semantic relationships where available
* precomputed vocabulary embeddings
* vector similarity search

The developer may use an appropriate open-source embedding model or other low-cost semantic retrieval technology.

Embeddings should preferably be generated during database construction and stored/indexed for later search.

Search should not require generating a new embedding for every vocabulary item at search time.

Only the teacher's search query needs to be converted into a semantic representation during a semantic search.

---

# 13. NO REQUIREMENT FOR LLM CLASSIFICATION

The application must NOT require an expensive external LLM to classify every vocabulary sense.

The developer should NOT implement a process in which hundreds of thousands of vocabulary senses are individually sent to an external LLM solely to determine their categories.

Automatic vocabulary relevance should instead make use of appropriate combinations of:

* existing source metadata
* lexical rules
* WordNet relationships
* CEFR information
* frequency information
* definitions
* translations
* semantic relationships
* embeddings
* deterministic taxonomy mapping
* other appropriate low-cost processing

An LLM may optionally be used during vocabulary construction for specific enrichment or quality-control tasks if economically and technically justified.

However, the system must remain functional without requiring an external LLM to classify the entire vocabulary database.

---

# 14. AUTOMATIC THEMATIC CLASSIFICATION

Vocabulary categories/topics should be assigned automatically where practical.

Teachers should NOT be required to manually categorize tens of thousands of vocabulary senses.

However, explicit manual classification of every vocabulary sense is NOT a prerequisite for semantic search.

The system may use:

* lexical metadata
* WordNet
* semantic relationships
* definitions
* translations
* rules
* taxonomy mapping
* embeddings
* other appropriate automated methods

A vocabulary sense may belong to more than one category when appropriate.

Categories should be treated as an additional retrieval and filtering mechanism rather than the sole mechanism for determining relevance.

# 16. THEME SEARCH

Teachers must be able to search for a theme and immediately browse vocabulary associated with that theme.

Example:

Teacher types:

COOKING

The database should return relevant cooking vocabulary.

The teacher can then apply additional filters:

COOKING + A2

or:

COOKING + A2 + HIGH PRIORITY

or:

COOKING + C2 + VERY HIGH PRIORITY

The teacher should not need to know individual English words before finding vocabulary within a topic.

Semantic search should also be available when the teacher's query does not correspond exactly to a predefined category.

---

# 17. VOCABULARY SEARCH

Teachers must be able to search by:

* English word
* English phrase
* Polish translation
* English definition
* sense
* topic/category
* CEFR level
* natural-language concept

Search should support both exact and semantic retrieval.

Examples:

`hotel`

`hotel room`

`hotel vocabulary`

`vacation`

`things I need at an airport`

`problems when traveling`

`words for describing personality`

Search results must clearly distinguish different senses of the same English word.

Search should return the most relevant vocabulary first while allowing the teacher to access all appropriate results.

The teacher must be able to combine search with filters.

---

# 18. HYBRID SEARCH ARCHITECTURE

The search system should combine multiple retrieval methods.

## 18.1 EXACT / TEXT SEARCH

Used for:

* exact English words
* phrases
* Polish translations
* definitions
* partial text matches

## 18.2 FILTER-BASED SEARCH

Used for:

* CEFR
* category
* subcategory
* part of speech
* priority
* frequency
* student
* assignment status
* learning state

## 18.3 SEMANTIC SEARCH

Used for conceptual searches such as:

"vacation"

"things at an airport"

"problems at a hotel"

"cooking vocabulary"

Semantic search should use precomputed embeddings or another appropriate vector representation.

## 18.4 RESULT COMBINATION

The system should be able to combine these signals into a relevance ranking.

For example:

SEARCH:

"vacation"

FILTER:

A2

PRIORITY:

HIGH+

STUDENT:

John

ASSIGNMENT:

NOT ASSIGNED

The system should return semantically relevant A2 vocabulary with high priority that John does not already have.

The exact ranking algorithm may be determined by the developer.

The implementation should favor speed, reliability, low operating cost and maintainability.

The teacher should be able to see many vocabulary rows at once.

The interface should prioritize:

* compact rows
* fast scrolling
* sorting
* filtering
* multi-selection

* large graphics

The teacher should be able to work efficiently with dozens of vocabulary senses visible on a desktop screen.

The teacher must also be able to copy vocabulary easily to send to students either:

* with translations
* without translations
* with definitions
* without definitions

This must work well at any stage of the learning process.

Teachers should be able to sort vocabulary by:

* English
* Polish
* CEFR

* frequency
* topic

Default sorting should prioritize useful vocabulary when appropriate.

The teacher must still be able to access and sort all vocabulary.

Examples:

Teachers can:

# 23. STUDENT MANAGEMENT

Teachers can:

* create students
* edit student information
* deactivate students
* reactivate students
* delete students
* open student profiles
* view assigned vocabulary
* view learning state
* view review information

No traditional student login/password system is required.

Students will be given vocabulary by the teacher after it is assigned by copying it from the vocabulary bank and pasting it into an external source such as a text message.

The teacher will then go over the vocabulary with the student manually.

---

# 24. STUDENT VOCABULARY RECORD

Each student has an independent learning record for each master vocabulary sense.

The relationship should be:

MASTER SENSE

↓

STUDENT VOCABULARY RECORD

The same master sense can therefore exist once globally while being associated with many students.

Student records must not duplicate the master vocabulary itself.

---

# 25. AUTOMATIC DUPLICATE MANAGEMENT

Duplicate prevention is a critical requirement.

The system must determine whether a student already has the exact master vocabulary sense.

It must NOT rely on English spelling alone.

Example:

BANK — financial institution

and

BANK — side of a river

are different senses and therefore different learning items.

However, if the teacher finds:

BANK — financial institution

through:

* COOKING
* MONEY
* search
* semantic search
* vocabulary set
* A2 filtering
* another topic

the system must recognize that it is the same master sense.

It must not create another student vocabulary record.

---

# 26. DUPLICATE RULES

Same master sense = duplicate.

Same English word but different sense = not duplicate.

Same sense found through different categories = duplicate.

Same sense found through different sets = duplicate.

Same sense found through different searches = duplicate.

The master vocabulary ID/sense ID should be the authoritative identity.

---

# 27. NOT-ASSIGNED FILTER

Teachers must be able to filter vocabulary to show only vocabulary not yet assigned to a particular student.

Example workflow:

1. Search COOKING
2. Select A2
3. Select Student John
4. Select NOT ASSIGNED
5. Review results
6. Select vocabulary
7. Assign

The teacher should immediately see only vocabulary John does not already have.

This is one of the most important teacher workflows.

---

# 28. BULK ASSIGNMENT

Teachers must be able to select multiple vocabulary senses and assign them to a student in one operation.

The system must prevent duplicate student records automatically.

Example result:

20 selected

18 new assignments

2 already assigned — skipped

The teacher should receive clear feedback after bulk assignment.

---

# 29. ASSIGNMENT

Teachers can assign:

* individual vocabulary senses
* multiple selected senses
* vocabulary sets
* filtered vocabulary
* search results

Assignment should create or activate the student's relationship with the selected master senses.

Assignment must not duplicate an existing student vocabulary record.

---

# 30. STUDENT LEARNING STATES

Each student vocabulary record should support a learning state.

Recommended conceptual states:

* NEW
* ASSIGNED
* ENCOUNTERED
* LEARNING
* REVIEWING
* MASTERED

The exact database implementation may be determined by the developer.

The teacher must be able to see the current state.

---

# 31. FSRS SPACED REPETITION

The platform must use FSRS.

SM-2 must not be used.

FSRS must determine the next review date based on the student's review performance.

The system must store the information required by FSRS to calculate future reviews.

Each student vocabulary sense has its own FSRS state.

---

# 32. MANUAL VOCABULARY REVIEW

The teacher must be able to conduct a manual review with a student.

The review does not require an interactive student application.

The teacher can present the vocabulary through the teacher interface and ask the student verbally or otherwise.

After the student responds, the teacher records the result.

At minimum:

* EASY
* MEDIUM
* HARD

The system then updates the student's FSRS state.

---

# 33. REVIEW RESULT PROCESSING

A review result must:

1. identify the student
2. identify the exact master vocabulary sense
3. record the review event
4. record the result
5. update FSRS
6. calculate the next review date
7. update the student's learning state where appropriate

The master vocabulary record must never be modified by the review.

---

The interface should show:

* English word/phrase

The teacher should be able to quickly mark:

EASY / MEDIUM / HARD

# 41. VOCABULARY DATA QUALITY

The database should preserve comprehensive lexical information while clearly identifying data quality.

Possible fields include:

* source
* source confidence
* translation confidence
* CEFR confidence
* example confidence
* category confidence
* sense confidence
* semantic confidence where applicable
* processing status

The system should preserve provenance wherever practical.

Low-confidence information should be identifiable without requiring the underlying vocabulary sense to be deleted.

---

# 42. TRANSLATION AVAILABILITY

Polish translations are strongly preferred.

However, a vocabulary sense should not automatically be deleted because a reliable Polish translation is unavailable.

The system should retain the English definition and clearly indicate missing or uncertain Polish translation information.

Teachers should be able to identify vocabulary with:

* reliable Polish translation
* multiple Polish translations
* uncertain translation
* missing Polish translation

---

# 43. EXAMPLE SENTENCES

Vocabulary senses should contain concise, natural example sentences.

Examples should:

* demonstrate the intended sense
* use natural English
* be appropriate for learners
* be appropriate for the vocabulary level where possible
* use American English spelling and usage by default

Examples should be associated with the correct sense.

# 45. VOCABULARY DATABASE CONSTRUCTION

The vocabulary-processing system should generally:

1. process source datasets
2. identify English lexical entries
3. preserve all supported relevant senses
4. extract Polish translations
5. extract English definitions
6. integrate CEFR information
7. integrate frequency information
8. integrate semantic information
9. identify lexical flags such as rare/archaic/technical where supported
10. identify or derive thematic information where practical
11. generate or select suitable example sentences where possible
12. calculate Vocabulary Priority
13. calculate confidence/quality indicators
14. generate semantic embeddings where semantic search is implemented
15. deduplicate at the sense level
16. perform data cleaning
17. perform quality control
18. generate the master vocabulary database

The exact internal pipeline may be designed by the developer.

The pipeline should favor:

* low operating cost
* reproducibility
* maintainability
* deterministic processing where practical
* open-source/local processing where practical

An external LLM must not be required to process every vocabulary sense.

---

# 46. SEMANTIC EMBEDDING REQUIREMENTS

If embeddings are used for semantic retrieval, they should be generated during vocabulary database construction rather than at every search.

The embedding representation should preferably be based on relevant sense information such as:

* English word/form
* English definition
* Polish translation where useful
* relevant lexical information
* semantic relationships where useful

The system should store or index the resulting vectors in a manner appropriate for fast similarity search.

The developer may use:

* PostgreSQL with pgvector
* another PostgreSQL-compatible vector solution
* another appropriate vector database

provided that the solution remains simple, maintainable and appropriate for the size of the vocabulary database.

The semantic search system must support hundreds of thousands of vocabulary senses without requiring an external AI API for every search.

# 49. SEARCH PERFORMANCE AND COST

Vocabulary search should be fast enough for live teaching.

Normal searches and filters should generally be handled directly by PostgreSQL.

Semantic search should use precomputed embeddings/vector indexes rather than external LLM classification.

The application should not make an external AI API request for every vocabulary row returned.

The application should not require processing the entire vocabulary database with an external LLM whenever the database is updated.

If an external AI service is used for optional enrichment, the developer must document:

* what it is used for
* approximate processing cost
* whether it is required
* whether the processing can be performed locally
* how the resulting data is stored

The production application should remain usable without an external LLM dependency for ordinary vocabulary searches.

# 57. CORE SUCCESS CRITERIA

The product is successful if the teacher can quickly perform the following workflow:

1. Open the vocabulary browser.

2. Enter a search such as:

   VACATION

3. Receive a useful list of semantically relevant vocabulary.

4. Optionally select a predefined topic such as:

   TRAVEL

5. Filter by a CEFR level such as:

   A2

6. Sort/filter by Vocabulary Priority.

7. See a dense list of useful vocabulary.

8. Select multiple vocabulary senses.

9. Select a student such as John.

10. Filter to NOT ASSIGNED.

11. Assign the selected vocabulary.

12. Receive clear confirmation of new versus already-assigned vocabulary.

13. Later open John's vocabulary.

14. Filter for DUE or OVERDUE vocabulary.

15. Conduct a manual review.

16. Mark each item EASY / MEDIUM / HARD.

17. Allow FSRS to calculate the next review date.

18. Return later and see what is due.

The system should make this workflow fast, reliable and simple.

# 58. FUNDAMENTAL DATA AND SEARCH PRINCIPLE

The master vocabulary database should be comprehensive.

Do not solve the problem of an enormous vocabulary database by deleting vocabulary.

Instead:

COMPREHENSIVE DATABASE

*

SENSE-LEVEL DATA

*

FREQUENCY

*

CEFR

*

VOCABULARY PRIORITY

*

LEXICAL / SEMANTIC INFORMATION

*

OPTIONAL THEMATIC CLASSIFICATION

*

SEMANTIC SEARCH

=================================

A large database that remains practical for teaching.

CEFR should describe difficulty.

Frequency should describe occurrence.

Vocabulary Priority should describe general learner usefulness.

Semantic search should identify vocabulary relevant to a concept.

Teacher Priority should describe individual teaching relevance.

Student Learning State should describe what the individual student currently knows and needs to review.

These concepts must remain separate in the system.

The system should not depend on manually categorizing every vocabulary sense.

The system should not depend on an expensive external LLM to classify the entire vocabulary database.

The primary goal is to give the teacher a fast and practical way to find the vocabulary they actually want to teach.
